# 参考片的「程序图形」语言：摄像机 · 透明 · 层次

> 分析对象：《1859-2026》82–101 秒（复数平面 / 临界线 / 质数分布）

## 一、这一镜到底发生了什么

逐帧测得的分段（10fps 采样）：

| 时间 | 画面 | 镜头 |
|---|---|---|
| 84–87s | 网格 + 金色竖线 + 零点点亮 | **快速前推**：坐标轴跨度 316→442px（+40%，2.5 秒） |
| 87–92s | 底部坐标轴滑入，质数标签 2 3 5 7 … | **二次前推**：572→696px（+22%，4.5 秒） |
| 93–96s | 每个零点发出一条正弦波 | 静止 |
| 96–101s | 波幅增大，底部浮现叠加后的阶梯 | 静止 |

逐帧缩放率：
- 常规帧 **+0.25%/帧**（= 7.5%/秒）
- 进入瞬间有一帧 **+2.25%**、下一帧 **+4.25%**（瞬时 42%/秒）

**总计约 1.7× 的推进，全部集中在 84–92 秒这 8 秒里。**

### 关键：推的是"图形空间"，不是素材

我们之前的引擎只会推素材（ken burns），而参考片推的是**整个图形世界**——
网格、坐标轴、波线、光点一起被推近，彼此间距等比放大。

这是两套完全不同的机制：
- 推素材 = 放大一张图片
- 推图形空间 = 加一个摄像机，所有元素跟着走

## 二、透明与层次：五层 alpha

在这一镜里同时叠了至少五层，每层透明度不同：

| 层 | 相对不透明度 | 说明 |
|---|---|---|
| 背景径向辉光 | ~0.10 | 深蓝，制造"空间感" |
| 网格 | **~0.05** | 几乎看不见，但存在 |
| 波线 | **~0.30** | 1.1px 细线，彼此可见不遮挡 |
| 坐标轴 / 刻度 / 数字 | ~0.60 | 比波线更实 |
| 零点光点 | 1.0 | 不透明 + 光晕 |

**规律：越靠后的层越淡。** 背景几乎看不见、网格勉强可见、内容层清晰。

对比我们的 `iso_bars`：三种面用了 0.50/0.72/0.50 的 alpha，没有"极淡的底层"，
所以看起来是"一块图"，不是"一个有纵深的场景"。

## 三、动态：不是所有东西一起动

这一镜的运动是**分层的、不同步的**：

| 元素 | 运动方式 |
|---|---|
| 摄像机 | 前推 1.7×，8 秒内完成 |
| 零点光点 | 亮度脉动，各自相位不同 |
| 波线 | 相位缓慢流动（`local * speed`），每条速度不同 |
| 叠加曲线 | 振幅随"波的加入"变大 |
| 坐标轴 | 从左侧伸展进来 |
| 字幕 | 逐句生长 |

**六个独立的动画轨道。** 我们目前的图元大多是"一个参数驱动全部"。

## 四、可直接复用的图形语法

### 4.1 前推镜头（dolly-in）

```json
"camera": { "s0": 1.0, "s1": 1.4, "t0": 0.0, "t1": 2.5, "ease": "easeInOut", "cy": 0.46 }
```

要点：
- 缩放 **1.3–1.8×**，时间窗 **2–8 秒**
- 用 `easeInOut`，结尾要停住（不要一直推）
- 中心点可以偏离画面中心（`cy`），推的过程中画面重心移动

### 4.2 波束 + 叠加（wave_stack）

N 条正弦波从左侧轴发出，下方画出它们的和。

```json
{ "kind": "wave_stack",
  "params": { "n": 14, "amp": 9, "span": 0.32,
              "rise": 1.4, "sum": true, "sumY": 0.74 } }
```

用途：把"多个频率叠加"这件事可视化——声音、信号、级数、傅里叶。

### 4.3 固定刻度轴（axis_labels）

数据锚点不随内容移动，让观众有"坐标系"可依靠。

## 五、引擎需要补的能力

| 能力 | 现状 | 说明 |
|---|---|---|
| **图形摄像机**（推拉/平移作用于所有图形） | ✅ 已实现 | 离屏缓冲 + `shot.camera`，与素材 ken burns 分离 |
| **波束 + 叠加** kind | ✅ 已实现 | `wave_stack`，含 `stagger` 逐条生长 |
| **固定刻度轴** kind | ✅ 已实现 | `axis_labels`，支持 `overlay` 不随摄像机变形 |
| **分层深度（视差）** | ✅ 已实现 | `graphics[].depth` 0–1，分三层，远层动得少、近层动得多 |
| **元素级独立动画轨道** | ✅ 已实现 | `graphics[].t0 / dur`，每个图元自己计时 |
| **非等比缩放（拉伸）** | ✅ 已实现 | `camera.sx0/sx1` 与 `sy0/sy1` 可不同 |
| **逐元素出现编排** | ✅ 部分 | `wave_stack` 支持 stagger；其他 kind 待补 |
| 真三维几何（透视网格/体） | ⚠️ 仅网格 | 需要 `proj` 接入图形层 |

### 实现要点

```json
"camera": {
  "s0": 1.0, "s1": 1.26,
  "sx0": 1.0, "sx1": 1.32,     // 横向多放大 6% → 拉伸
  "sy0": 1.0, "sy1": 1.22,
  "t0": 0.2, "t1": 4.8,
  "ease": "easeInOut",
  "cy": 0.44,                  // 推的中心略偏上
  "parallax": 0.6              // 0=不分层，1=按深度全视差
}
```

```json
"graphics": [
  { "kind": "grid2d",   "depth": 0.2, "t0": 0.0, "params": { "alpha": 0.05 } },
  { "kind": "wave_stack","depth": 0.7, "t0": 0.15,"params": { "n": 15, "stagger": 0.04 } },
  { "kind": "axis_labels","overlay": true, "t0": 0.8, "params": { ... } }
]
```

- `depth` 越小越远：摄像机推近时它动得少 → 产生视差
- `overlay: true`：完全不参与摄像机变换（坐标轴、刻度数字），保证文字不被拉伸
- `t0`：该元素从镜头第几秒开始出现

## 六、架构含义：需要有"跨模块的通用能力"

这次分析暴露了一个设计问题：

**如果每个图形 kind 自己处理运动，就会各自为政。**
摄像机必须是**跨模块的横切能力**——资产、图形、文字都能被同一个摄像机推近，
但各自的变换规则不同（素材做 ken burns、图形做 push、文字保持稳定）。

所以引擎的核心不是"kind 越多越好"，而是三层：

```
场景图（Scene Graph）
  每个镜头 = 一棵元素树
  每个元素有：本地变换 / 深度 / 材质（alpha, glow）
        ↓
摄像机（Camera）
  统一变换：推拉、平移、旋转
  可选视差：按深度分层
        ↓
合成器（Compositor）
  分层 alpha + bloom + 暗角 + 颗粒
        ↓
  帧
```

**摄像机与合成器是"能力"，kind 是"内容"。** 两者分开，才不会每加一种视觉就重写一遍运动逻辑。

这条结论直接影响下一步：与其继续堆 kind，不如先把"场景图 + 摄像机 + 合成器"这三件套做实。
